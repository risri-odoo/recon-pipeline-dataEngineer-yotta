# Design decisions

One dated line per decision.

- 2026-11-15: Console script `recon` points at `recon.presentation.cli:main`; `python -m recon` delegates to the same entry point.
- 2026-11-15: Dev tooling lives in a local `.venv` (gitignored); pytest declared as the `dev` optional dependency in pyproject.toml.
- 2026-11-15: `.gitattributes` forces LF for text (`* text=auto eol=lf`, `*.json text eol=lf`) and marks `*.csv -text` so git never rewrites CSV bytes; file hashes and byte-identical report tests must not depend on the OS.
- 2026-11-15: All CSV writers open files with `newline=""` and use `lineterminator="\n"`, so output bytes are identical on Windows and Linux.
- 2026-11-15: SILVER gains `ref_customer(run_id, customer_id, customer_name)`, PK (run_id, customer_id), holding the validated reference customers (CLAUDE.md rule 2 updated).
- 2026-11-15: Batch warnings get no table: one check_result row per warning check (SCHEMA_DRIFT, MISSING_OPTIONAL_COLUMN, EMPTY_BATCH) with JSON detail `[{side, columns}]`, plus a `warnings` array in report.json.
- 2026-11-15: KEY_UNIQUENESS, REFERENTIAL_INTEGRITY and KEY_COVERAGE are engine invariants; a failure is a bug, so the run rolls back to FAILED with failure_reason `INVARIANT_VIOLATION:<check>` and counts in failure_detail.
- 2026-11-15: Data problems (rejects, conflicts, mismatches) affect only recon_status, never run status.
- 2026-11-15: Backfill = `recon backfill --manifest PATH`, manifest columns batch_id, source_path, target_path, reference_path; one independent run per line in order, continue past failures, print a summary table, skip SUCCEEDED pairs on re-run.
- 2026-11-15: Fractional seconds are accepted and truncated to whole seconds (warehouses commonly truncate ms; second precision avoids false mismatches).
- 2026-11-15: Batch rejects are not stored in quarantine: the data transaction rolls back and the separately committed run row gets status REJECTED, failure_reason = code, failure_detail = detail.
- 2026-11-15: A rejected newest version never falls back to an older valid one: the key becomes SOURCE_REJECTED / TARGET_REJECTED and older valid rows are SUPERSEDED; version ordering uses updated_at whenever it parsed, and rows with an unparsed updated_at cannot win.
- 2026-11-15: Stale RUNNING: started_at older than `--stale-after-minutes` (default 60) becomes ABANDONED; otherwise exit 2 "run in progress" and no row is created; no PID checks.
- 2026-11-15: SKIPPED keeps its run row (skipped_of_run_id), does not rewrite report files, prints the existing report path and returns that run's exit code; no new bronze data, silver or gold rows.
- 2026-11-15: Known limitations: all currencies treated as 2 decimals (JPY, KWD unsupported); currency codes not checked against ISO 4217.
- 2026-11-15: A key rejected on both sides keeps SOURCE_REJECTED and gets key_result.note = 'rejected on both sides'.
- 2026-11-15: run columns renamed for clarity: recon_result -> recon_status, error_detail -> failure_reason + failure_detail, skipped_of -> skipped_of_run_id.
- 2026-11-15: SRC_ROW_ACCOUNTING, TGT_ROW_ACCOUNTING and AGGREGATE_EXPLAINED are also INVARIANT checks (a failure means FAILED run with INVARIANT_VIOLATION:<check>).
- 2026-11-15: recon_status = PASS iff every key_result row is MATCHED and there is no SOURCE/TARGET ROW_REJECT without an order_id; otherwise FAIL.
- 2026-11-15: A SKIPPED invocation writes only its own run row; nothing else in bronze, silver or gold.
- 2026-11-15: A tie at max updated_at between a rejected and a valid row is treated as rejected (conservative): key *_REJECTED, valid rows SUPERSEDED with detail "shadowed by rejected line N".
- 2026-11-15: Blank lines (empty or whitespace-only) are not landed in raw_record and not quarantined; counted per side as metrics blank_lines; row accounting covers landed DATA records only.
- 2026-11-15: Config shape: `fields` list (order = validation order) with types str|enum|decimal|timestamp; top-level `business_key`, `version_field`, `compare_fields`, `columns.source/target`, `reference`, `aggregates.sum_fields/group_by`; unknown keys anywhere are a ConfigError.
- 2026-11-15: Decimal config values (`min`, `tolerance`) must be JSON strings, never JSON numbers, so no float ever enters the config; tolerance is stored as integer minor units (0.01 -> 1).
- 2026-11-15: config_sha256 hashes the raw config with per-type defaults filled in (required=false; str upper=false, pattern=null, reference=false; decimal scale=2, min=null, tolerance="0").
- 2026-11-15: Currency shape is expressed as str + `pattern: ^[A-Z]{3}$` (applied after upper-casing) rather than a dedicated type.
- 2026-11-15: BAD_FORMAT vs BAD_TYPE: money is BAD_FORMAT if, after removing currency-symbol characters, it looks numeric (digits with , . sign or exponent), else BAD_TYPE; a timestamp is BAD_FORMAT if it looks like a date (d-d-d, d/d/d, d.d.d) but not the accepted form, BAD_TYPE otherwise or when the calendar date/time/offset is impossible.
- 2026-11-15: Physical column names (side maps and reference.columns values) are not snake_case-checked: they are normalized with trim + lower-case (same as headers), must be non-empty after that, and must be unique per side after normalization. Logical field names stay strict snake_case.
- 2026-11-15: validate_row takes an optional reference-id set; INVALID_REFERENCE is added only when every other field passed.
- 2026-11-15: Generator (`recon/generator`) is a standalone package that never imports recon.service/recon.repository (enforced by an AST test); expected answers come only from its own per-line bookkeeping. The CLI may import it (it is not the repository tier).
- 2026-11-15: Generator bucket size = max(1, floor(N * rate)) with rates as integer per-mille; one `rng.sample` of base indices is sliced in a fixed scenario order, so buckets are disjoint by construction; N below the number of base-key scenarios (16) is an error.
- 2026-11-15: Generated files are `source.csv`, `target.csv`, `customers.csv`; source is written in business-key order, target shuffled with the same rng; ~N/50 customers = max(1, N // 50) (superseded below: floor of 5).
- 2026-11-15: src_malformed keys keep a valid target row, so their expected key status is EXTRA_IN_TARGET (a MALFORMED_ROW has no trusted order_id) and they count in `unattributable_rejects`.
- 2026-11-15: Injected bad values: BAD_TYPE = amount `abc` or order_ts `yesterday`; MISSING_REQUIRED blanks one of customer_id/order_ts/status/amount/currency (never order_id or updated_at, so the key and version stay attributable); INVALID_REFERENCE uses `CX<n>`; MALFORMED_ROW appends one extra field.
- 2026-11-15: expected/<name>.json includes `scenario_keys` (superseded below: only when N <= 1000), all key statuses and row-reject codes with zero counts for a stable shape, field diffs as a list of {field_name, diff_type, count}, and sums as 2-decimal strings.
- 2026-11-15: expected/<name>.json writes per-scenario key lists (`scenario_keys`) only when N <= SMALL_N_KEY_LISTS (1000); larger runs keep counts only (`bucket_sizes`, key/diff/reject counts). The in-memory Dataset always carries the buckets for tests.
- 2026-11-15: Generator customer count = max(5, N // 50), so the 60-row sample has several customers; data/sample and data/expected/sample.json regenerated.
- 2026-11-15: Input file names are arbitrary CLI paths (DESIGN.md 2.2 updated); the generator writes source.csv, target.csv, customers.csv.
- 2026-11-15: CLAUDE.md rule 10: Claude never runs git commit, git add or any git write command; the user reviews and commits every step.
- 2026-11-15: raw_record follows DESIGN (record_type HEADER/DATA, no field_count/fields_json); malformed data records are landed verbatim and judged later by validation re-parsing raw_text.
- 2026-11-15: The run row has finished_at (not ended_at) and no metrics_json column; metrics stay in metrics.json only (DESIGN 7.1 #13).
- 2026-11-15: "Index on (run_id, side, record_key)" maps to the business key: clean_record PK (run_id, side, order_id) and index ix_quarantine_key (run_id, side, order_id); raw_record is keyed by its PK (run_id, side, line_no); plus ix_key_result_status (run_id, key_status).
- 2026-11-15: DDL enforces the DESIGN catalogues with CHECK constraints and uses foreign keys: every table -> run(run_id); clean_record and quarantine (run_id, side, line_no) -> raw_record; field_diff (run_id, order_id) -> key_result.
- 2026-11-15: connect() opens SQLite in autocommit mode (isolation_level=None) with foreign_keys=ON and busy_timeout=5000; transaction() is BEGIN IMMEDIATE, rolls back on any exception and refuses to nest. Repository functions never manage transactions; the service decides the boundaries.
- 2026-11-15: Ingest is two passes per file: (1) check_file streams raw bytes once for sha256 + strict UTF-8 (BOM stripped) and reads the header; (2) land_file streams records into raw_record in executemany chunks of 5000. If any side has a batch reject, nothing is landed for any side.
- 2026-11-15: The header is the first non-blank record; leading blank lines are counted as blank_lines and the header keeps its physical line_no. The HEADER record is landed in raw_record.
- 2026-11-15: Batch reject order within one file: FILE_NOT_FOUND, EMPTY_FILE, ENCODING_ERROR, then both DUPLICATE_HEADER and SCHEMA_MISSING_COLUMN when both apply. A header record that the csv module cannot parse is EMPTY_FILE (superseded below: MALFORMED_FILE).
- 2026-11-15: REFERENCE side: only reference.key (customer_id) is required; other reference columns (customer_name) are optional, so missing ones give MISSING_OPTIONAL_COLUMN.
- 2026-11-15: Record boundaries come from csv.reader (non-strict) over a wrapped line iterator; raw_text = the consumed physical lines minus the final terminator (CRLF, LF or CR), with internal line breaks kept as-is. A blank line is a one-line record that is whitespace-only.
- 2026-11-15: New batch reject MALFORMED_FILE (signed off): (a) the header record fails a strict CSV parse, or (b) the file ends inside an open quoted field; detail names the line_no where the open record started. Checked after ENCODING_ERROR and before the header checks, and it stops that file's checks. EMPTY_FILE is no longer used for these. DESIGN 4.1 and the catalogue note updated.
- 2026-11-15: The unterminated quote is detected by a small quote-state scanner (ends_in_open_quote) that mirrors csv.reader's default non-strict dialect, because csv.reader silently accepts an open quote at EOF. Only the last record can be open, so the check pass scans every record once and tests the last one.
- 2026-11-15: land_file re-hashes the raw bytes as it reads them (hashing raw stream under the text wrapper). If the result differs from the check-pass sha256 (or the file vanished, hash `MISSING`, or no longer decodes), it raises InputChangedError; the run becomes FAILED with failure_reason INPUT_CHANGED and failure_detail JSON {side, file, expected_sha256, actual_sha256}, exit 2. DESIGN 3 (run.failure_reason/detail) and the lifecycle diagram updated.
- 2026-11-15: Composite business keys: config `business_key` is a field name or a non-empty list of distinct required, non-decimal fields (never the version_field, never in compare_fields); Config.business_key is a tuple. A composite key joins components with '|', escaping '\' -> '\\' and '|' -> '\|' inside components (single keys are unescaped); the joined key is stored in the existing order_id columns. A string key keeps its config hash.
- 2026-11-15: Where the step-5 prompt and DESIGN 4.4 differ, DESIGN wins: rejected rows whose updated_at parsed take part in version ordering (a reject at max_u shadows the key), and in a conflict only the rows at max_u are CONFLICTING_DUPLICATE; older valid rows are SUPERSEDED.
- 2026-11-15: payload_sha256 = sha256 of the compact JSON array of all logical fields in config order, NULL as `\N`, money as integer minor-unit text.
- 2026-11-15: Validation re-reads raw_record and re-parses each record strictly (csv strict=True); a strict-parse failure or a field count different from the landed HEADER is MALFORMED_ROW with order_id/updated_at NULL. Column positions are re-derived from the landed HEADER record.
- 2026-11-15: Reference rows: MALFORMED_ROW also applies; customer_id is trim + upper-case only (no pattern); customer_name is trimmed, empty -> NULL; the validated id set is built once in memory and passed to both order sides.
- 2026-11-15: Duplicate dispositions have field_name NULL and carry order_id + updated_at; details: "exact duplicate of line N", "superseded by line N (updated_at U)", "shadowed by rejected line N", "K different payloads at updated_at U on lines ...".
- 2026-11-15: build_silver (SILVER stage orchestration: reference -> validate -> dedupe -> write) lives in recon/service/dedupe.py until pipeline.py exists; SideCounts gives rows_read, accepted, rejected, duplicate_exact, superseded, conflicting_rows per side, with dispositions counted apart from rejects.
- 2026-11-15: pytest `pythonpath = ["."]` so shared test helpers (tests/silver_helpers.py) import the same way under `pytest` and `python -m pytest`.
- 2026-11-15: A key whose only rows are TARGET ROW_REJECTs (nothing on SOURCE) is TARGET_REJECTED, mirroring SOURCE_REJECTED for a source-only reject (signed off); DESIGN 4.5 TARGET_REJECTED condition updated.
- 2026-11-15: Where the step-6 prompt and DESIGN differ, DESIGN wins: aggregate_result stores delta / explained_delta / unexplained_delta (no MATCH/DIFF); an INVARIANT failure raises InvariantViolation before any check_result row is written and the caller's transaction rolls back; all nine checks are written (incl. MISSING_OPTIONAL_COLUMN); recon_status follows DESIGN 4.8 (also FAIL on an unattributable ROW_REJECT).
- 2026-11-15: GOLD entry point is compare.reconcile(conn, run_id, config, warnings) inside the caller's transaction; it does not touch the run row (the pipeline step will).
- 2026-11-15: key_result deciding line per side: the clean row, else the lowest CONFLICTING_DUPLICATE line, else the newest ROW_REJECT by updated_at (lowest line on a tie, unparsed updated_at last); SUPERSEDED / DUPLICATE_EXACT rows never decide.
- 2026-11-15: Because field_diff has a foreign key to key_result, key_result is inserted first (both-sides keys as MATCHED), then field_diff, then one UPDATE sets diff_count and turns keys with diffs into MISMATCHED.
- 2026-11-15: field_diff is one INSERT ... SELECT with a UNION ALL branch per compare field; money values are rendered by the SQLite function recon_format_minor(units, scale), which wraps normalize.format_minor and is passed in by the service so the repository never imports the service tier; tolerance and scale are bound parameters; config-derived identifiers must match ^[a-z][a-z0-9_]*$ before interpolation.
- 2026-11-15: Aggregates: metrics ROW_COUNT and SUM_<FIELD>, group_by ALL and <FIELD> upper-cased; the ALL row is always written (0 when empty); a NULL group value is the string 'NULL'; explained_delta walks key_result joined to the clean rows, with NULL measure values counted as 0.
- 2026-11-15: AGGREGATE_EXPLAINED detail stores, per metric over group ALL, {delta, source_only, target_only, both_sides} split by clean-row presence (not by key status, so TARGET_REJECTED and one-sided CONFLICT keys are included); PASS also requires delta = source_only - target_only + both_sides.
- 2026-11-15: Check rows: invariant checks put the compared counts in expected/actual and the counts as canonical JSON in detail (which becomes failure_detail on a violation); warning checks use expected "0", actual = number of sides affected, and sort detail by SOURCE, TARGET, REFERENCE (the same order as the report's warnings).
- 2026-11-15: aggregate_result.metric and group_by have no CHECK constraints: their values come from the config (ROW_COUNT / SUM_<sum_field>, ALL / <group_by field>, upper-cased) and are validated in config.py. CHECKs stay only on fixed catalogues (sides, run/key/check statuses, categories, diff types, severities, record types).
- 2026-11-15: config.py rejects a group_by field named `all`, because its upper-cased name would collide with the reserved ALL grouping in aggregate_result.group_by.
- 2026-11-15: Where the step-7 prompt and DESIGN/DECISIONS differ, DESIGN wins: the run row uses finished_at (not ended_at) and has no metrics_json column (metrics go to out/<run_id>/metrics.json); only RUNNING attempts older than --stale-after-minutes become ABANDONED (a fresh one gives "run in progress", exit 2, nothing written); SKIPPED records its own run row; the SUCCEEDED update commits inside the data transaction.
- 2026-11-15: config.py rejects a decimal field in aggregates.group_by (money is a measure, never a grouping).
- 2026-11-15: build_silver moved from dedupe.py to pipeline.py (the SILVER stage orchestration now lives with the other stages).
- 2026-11-15: The batch-check pass runs before the run row exists (its sha256s form run_key); the data transaction reuses those checks, raises BatchRejected inside BEGIN IMMEDIATE when any exist, and landing re-hashes the bytes (INPUT_CHANGED on a difference).
- 2026-11-15: The run-admin step (SKIPPED check, run-in-progress check, stale -> ABANDONED, RUNNING insert) is one BEGIN IMMEDIATE transaction, so two invocations cannot take the same attempt number.
- 2026-11-15: A SKIPPED row takes the next attempt number (attempt = existing rows + 1, SKIPPED and ABANDONED included); SKIPPED reuses the latest SUCCEEDED attempt and copies its recon_status and exit_code.
- 2026-11-15: Errors before a run row can exist (bad config, unknown RECON_FAIL_AT, negative --stale-after-minutes) exit 2 with a message and write nothing; the CLI maps any unexpected exception to exit 2, never 1 (1 means recon FAIL).
- 2026-11-15: Fault injection RECON_FAIL_AT in {after_bronze, after_silver, after_gold} raises RuntimeError inside the data transaction; like any unexpected exception it ends as FAILED, failure_reason UNEXPECTED_ERROR, failure_detail "<ExceptionType>: <message>".
- 2026-11-15: Logs are key=value lines (ts level run_id stage event, then event fields; values with whitespace, '=' or '"' JSON-quoted, '-' for unknown) on stderr and in out/<run_id>/run.log (UTF-8, LF, rewritten per run); SKIPPED and run-in-progress log to stderr only and create no output dir.
- 2026-11-15: metrics.json stages: batch_checks, bronze, silver, gold, each with duration_ms (perf_counter) and per-side rows_in/rows_out/rows_rejected. Bronze: rows_in = data records + blank_lines, rows_out = landed data records. Silver: rows_out = clean rows, rows_rejected = ROW_REJECTs, plus duplicate_exact/superseded/conflicting_rows (REFERENCE: duplicates_ignored). --profile-memory adds tracemalloc peaks per stage (reset_peak between stages) and overall.
- 2026-11-15: `recon run` prints one key=value line on stdout (status, run_id, attempt, recon_status, exit_code, failure_reason when set, out). For SKIPPED, run_id is the reused SUCCEEDED run and skip_run_id is the new SKIPPED row.
- 2026-11-15: Stale + fresh RUNNING together (signed off): stale attempts are marked ABANDONED first and that update is committed; if a fresh RUNNING attempt remains, the invocation then reports "run in progress" (exit 2) and creates no new row. Supersedes "nothing written" in the step-7 line above; DESIGN 6.5 updated.
- 2026-11-15: run.log added to the out/<run_id>/ outputs in the DESIGN flow diagram (signed off).
- 2026-11-15: Backfill is `recon backfill --manifest PATH --config PATH` with the same --db/--out/--stale-after-minutes/--profile-memory options as `recon run` (no --force); the manifest has no config column, so one config applies to every line.
- 2026-11-15: Manifest validation (all before any run, exit 2, no DB created): file missing or not UTF-8, strict CSV parse error, no header, header-only, missing / unknown / duplicate column (names trimmed + lower-cased, any order), wrong field count, empty batch_id or path, duplicate batch_id. Blank lines are ignored. The config, RECON_FAIL_AT and --stale-after-minutes are also validated up front.
- 2026-11-15: Relative manifest paths resolve against the manifest's directory, not the CWD, so a manifest is portable with its data; the run row stores the resolved path.
- 2026-11-15: Backfill summary statuses: the run status, or IN_PROGRESS (blocked by a fresh RUNNING attempt; run_id = that attempt) or ERROR (an exception escaped run_pipeline; run_id '-'); both have exit_code 2. For SKIPPED, run_id is the reused SUCCEEDED run. The table is fixed-width on stdout, sorted by batch_id (code-point order); metrics.json is written per executed line.
- 2026-11-15: Where the step-8 prompt and DESIGN differ, DESIGN wins: report files are `report.json` and `mismatches.csv` (not recon_report.json / mismatched_records.csv); the run row's `finished_at` is reported (not ended_at); durations stay in metrics.json only, never in report.json. `field_diffs.csv` and `summary.md` are added to the out/<run_id>/ outputs (DESIGN flow diagram updated).
- 2026-11-15: DESIGN 7.1 #12 updated (signed off): the report files are byte-identical for the same inputs + config apart from run timestamps (started_at, finished_at in report.json and summary.md); run.log and metrics.json are the non-deterministic outputs.
- 2026-11-15: `run.config_json` (signed off) stores the canonical config JSON that config_sha256 hashes, on every RUNNING and SKIPPED row, so `recon report --run-id ID` needs only --db/--out; the report refuses a config_json whose sha256 differs from config_sha256. The column is nullable so older/test rows stay valid; a run without it cannot be reported.
- 2026-11-15: Report model lives in recon/service/report.py (reads via the repository, streams CSV rows from cursors); recon/presentation/report_writer.py only serializes. Presentation never imports recon.repository and no SQL string appears outside recon/repository (enforced by tests/unit/test_architecture.py).
- 2026-11-15: Atomic publish: the five report files are written into `out/.<run_id>.staging`, the run dir's other files (run.log, metrics.json) are copied in, then the run dir is renamed to `.<run_id>.old`, staging renamed into place and the old dir deleted. recover_run_dir finishes an interrupted swap (old dir without run dir -> restored; both -> old removed; staging -> removed).
- 2026-11-15: Reports are written only for SUCCEEDED runs (and each SUCCEEDED backfill line). If the report cannot be written after a SUCCEEDED run, the CLI prints the error with a `recon report --run-id` hint and exits 2 (the run row stays SUCCEEDED).
- 2026-11-15: SKIPPED prints `report=<out>/<reused run_id>/report.json` and never writes; if that file is missing it only warns on stderr with the `recon report` hint. `recon report` on a non-SUCCEEDED run (incl. SKIPPED, naming the reused run) exits 2; on success it exits 0 and prints run_id and report path.
- 2026-11-15: mismatches.csv columns: record_key, key_status, differing_columns (sorted, `;`), note, source_state/target_state (CLEAN, the deciding quarantine reason_code, or ABSENT), source_line_no/target_line_no, then source_<f>/target_<f> pairs for every logical field except business-key fields, in config order (updated_at included). Values only for CLEAN sides; money as fixed-point text.
- 2026-11-15: quarantine.csv keeps exactly the requested columns (side, source_file, line_no, reason_code, detail, raw_text), sorted SOURCE -> TARGET -> REFERENCE then line_no; run_id is the directory name and in report.json.
- 2026-11-15: report.json money aggregates stay integer minor units with `unit` (ROWS | MINOR_UNITS) and `scale` beside them; field_diff_counts and key_status_counts are zero-filled for a stable shape; aggregate_explanation adds a per-key-status split of each overall delta (sums to the delta) next to the source_only / target_only / both_sides split.
- 2026-11-15: summary.md orders sections by catalogue (sides SOURCE->TARGET->REFERENCE, DESIGN key-status and diff-type order), never by dict order, so it renders identically from the in-memory report and from the parsed report.json; Markdown cells escape `\` and `|` so composite keys cannot break tables.
- 2026-11-15: Every CSV export (mismatches.csv, field_diffs.csv, quarantine.csv) starts with a run_id column, so each exported row is traceable on its own (supersedes "quarantine.csv keeps exactly the requested columns" above). A --force attempt's CSVs therefore differ from attempt 1 only in that column.
- 2026-11-15: DESIGN 7.2 known limitations gain: no schema migrations (a DB from before a schema change must be recreated) and the Windows folder swap failing on a locked file (previous folder restored, exit 2, rerun `recon report`).
- 2026-11-15: Step 9 test matrix lives in docs/TEST_MATRIX.md (one row per edge case: level, expected behaviour, test, status covered/added; untested cases listed as proposals awaiting approval). End-to-end tests live in tests/e2e/.
- 2026-11-15: Where the step-9 prompt and DESIGN differ, DESIGN wins: the determinism test compares `report.json` (not recon_report.json).
- 2026-11-15: Shuffled-input determinism masks, besides run timestamps and input hashes, what derives from the hashes (run_key, run_id) and physical line numbers (mismatch_samples source/target_line_no, mismatches.csv line columns), because line_no is the physical line by design (rule 6); every other field must be identical.
- 2026-11-15: The 10k end-to-end test compares every result field of expected/<name>.json with report.json and fails if expected gains an unmapped field; generator metadata (bucket_sizes, generator_version, n, seed, scenario_keys) describes the generator, not the reconciliation, and is not compared.
- 2026-11-15: Invariant-violation tests simulate engine bugs by faking one repository count per check (KEY_UNIQUENESS cannot be violated through the DB because primary keys forbid it).
- 2026-11-15: P1 (signed off): decimal fields take an optional `max` (decimal string, default null, part of the config hash); orders amount and discount max "9999999999.99". A value above max (or below min) is an OUT_OF_RANGE row reject, never a run failure. DESIGN 2.1 and 4.3 updated.
- 2026-11-15: P1 headroom: MONEY_LIMIT_MINOR = (2^63 - 1) // 1,000,000 = 9223372036854 minor units, so at least a million values at the limit sum inside int64. Configured min/max must lie within +/- that limit (ConfigError otherwise); a field with no configured bound uses it as the bound (OUT_OF_RANGE beyond it), so no value can overflow SQLite INTEGER on insert.
- 2026-11-15: P2 (signed off): SQLite `integer overflow` while building aggregates or the AGGREGATE_EXPLAINED breakdown makes the run FAILED with failure_reason AGGREGATE_OVERFLOW and failure_detail {error, step} (step aggregates | checks), exit 2, data rolled back. The repository's db.is_integer_overflow recognizes the error; compare.AggregateOverflow carries it. With the orders max one SUM overflows only past ~9.22 million max-value rows on one side (DESIGN 7.2 #6).
- 2026-11-15: P4 (signed off): upper-case normalization of str fields (and the reference key) maps only ASCII a-z to A-Z; other characters are kept, so 'straße' -> 'STRAßE' stays distinct from 'STRASSE'. Enum matching keeps str.upper() (outside the decision's scope; superseded below: enums are ASCII-only too). DESIGN 7.1 #16 added.
